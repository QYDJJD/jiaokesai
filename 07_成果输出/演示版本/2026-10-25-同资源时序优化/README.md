# 情景库演示改版：同资源时序优化

直接双击打开 [情景库演示-同资源时序优化.html](情景库演示-同资源时序优化.html)。页面不需要安装依赖或联网，HTML 内包含全部计算和界面代码，可单独发送给其他人。

## 这一版改了什么模型

原演示把增援时刻写死：备用公交从第13、15、17分钟发车，出租从第13分钟增加供给。本版新增“从可行候选时刻中选择投入安排”的求解过程。

输入是预计到达曲线、人数、时段和备用公交周转时间；模型输出3辆备用公交的首发时刻与出租增援流的开始时刻。公交后两趟按相同周转间隔安排。

本版专门验证“调整投入时序是否能够降低等待”，尚未实现旅客方式重分配、线路优化、方向分配或预测不确定性下的滚动调度。

## 怎样保证对照有意义

页面比较三个方案：

| 方案 | 常态服务 | 备用公交 | 出租增援 | 投入时刻 |
|---|---|---|---|---|
| 无增援 | 相同 | 0 | 0 | 仅常态安排 |
| 固定时刻增援 | 相同 | 3辆、每辆3趟、共9趟 | 120辆次 | 预先固定 |
| 模型安排增援 | 相同 | 3辆、每辆3趟、共9趟 | 120辆次 | 模型从可行时刻中选择 |

公交每趟40人；出租每辆2人、每分钟增援2辆、持续60分钟。固定与模型方案均有600个计划增援席位，空载班次也计入投入。两个方案使用完全相同的旅客身份、到达时刻、步行时间和方式分配。

这里固定的是车辆数、趟次、容量和到位下界，并未固定全部资源占用时长。推迟投放可能改变车辆结束任务的时间，当前没有计算待命成本、人员工时或机会成本，因此不能据此宣称成本最优。

为进行有限资源对照，本版将原演示中连续追加的出租增援截成120辆次，将备用公交限定为每辆3趟。因此本版的指标应在本版内部比较，不能直接与原HTML中的所有结果拼接。

## 决策、目标和约束

### 决策变量

- 备用公交1、2、3的首发时刻；
- 出租增援流的首次发车时刻。

### 优化目标

最小化所有旅客从到达接续点至发车的总等待时间。在旅客人数相同的情况下，这等价于最小化平均候车时间。

导出字段 `objective` 为全部旅客总等待（人·分钟）；`variableObjective` 为公交与出租可优化部分，`constantMetroWait` 为地铁固定部分。timing-01.1修正日间导出漏计固定地铁等待的问题，候选比较与排班选择不变。

候客峰值和全部发车时间另行报告；它们不是本次求解的联合目标，不能保证每个指标都同时改善。

### 可行约束

1. 公交最早首发分别为第13、15、17分钟，首发候选截至第42分钟，采用整数分钟。
2. 同一备用公交只安排3趟，后续发车间隔固定为所选周转时间30或60分钟。
3. 公交共用一个上客泊位；每班发车前1分钟为上客窗口，相邻发车至少间隔1分钟，不能与常态班次重叠。
4. 出租增援首次发车候选为第13至72分钟；持续60分钟，每分钟增援2辆，不能提前使用增援能力。
5. 各方式按旅客到达接续点的先后顺序服务；每班载客不超限。
6. 每位旅客的接续方式保持固定，当前不能让公交替代出租或地铁。

### 求解方法

枚举可行公交首发组合，计算每个组合的总等待；另枚举60个出租增援起点。固定方案始终保留在候选集中；候车目标相同时保留固定安排。

因为当前各方式需求固定，没有跨方式资源争用，也没有旅客在方式之间重新分配，各方式的等待目标可分开最小化。这个分解只适用于当前简化模型；以后增加共用道路瓶颈、跨方式调配或方式选择后，需要重新设计联合求解过程。

“择优”只指上述候选策略和约束范围内的选择，不代表全体实际调度策略的全局最优。

## 默认示例结果

条件：夜间、800人、持续30分钟、80%旅客在最后1/3时段进入、备用公交周转30分钟。

| 指标 | 无增援 | 固定时刻增援 | 模型安排增援 |
|---|---:|---:|---:|
| 平均候车 | 70.175分钟 | 23.5125分钟 | 18.84625分钟 |
| 候客峰值 | 666人 | 579人 | 500人 |
| 全部发车 | 第220分钟 | 第115分钟 | 第86分钟 |

模型将备用公交首发从13、15、17分钟调整为17、24、26分钟，出租增援起点仍为13分钟。延后部分公交首发及后续班次，使有限的公交席位更好地覆盖后段集中到达的旅客。相对固定方案，平均候车降低约19.8%，峰值减少79人，全部发车提前29分钟。

切换到“夜间·前段集中”，固定与模型方案的平均候车均为27.3325分钟，没有改善。页面保留这个结果，用于说明模型并非在每个情景中都会改变方案。

上述均为合成参数下的计算结果，不代表虹桥实测改善率或真实可执行调度。

## 建议怎样看

1. 先看默认“夜间·后段集中”，比较两个相同增援投入方案。
2. 查看“模型具体改了哪些时刻”，确认改变的是发车安排。
3. 切换“夜间·前段集中”，观察无改善时模型保留固定安排。
4. 修改持续时间、人数或公交周转时间，重新计算。
5. 拖动过程时间，查看各方式候客人数及旅客守恒。
6. 使用“导出本次计算JSON”保留输入、预算、方案和指标，便于复核。

修改输入后旧结果会标记失效，重新计算前不能导出旧结果。

## 验证记录

运行：

```powershell
node .\验证模型.cjs
```

已通过14组情景、42次方案运行的检查，涵盖白天/夜间、三种节奏、零人数及人数边界、持续时间和公交周转变化。检查包括：

- 旅客数量及身份守恒；
- 上客、发车与步行时序；
- 先到先服务及班次载客上限；
- 公交上客窗口不重叠；
- 两个增援方案的车辆、趟次和计划容量相同；
- 备用公交最早到位及周转约束；
- 过程人数守恒、峰值独立核算；
- 模型等待目标不劣于保留的固定方案；
- 相同输入下常态服务不随方案改变。

浏览器已核对默认输出、无改善示例、修改参数后的结果失效、方案切换、过程结束时全部旅客完成发车，以及JSON下载；未发现浏览器控制台错误。
