# 情景调度研究平台

版本：PLATFORM-01。日期：2026年10月20日。

这是运行在本机浏览器中的研究平台，连接现有[接续运输优化原型](../接续运输优化原型/README.md)。可以录入其他事件，也可以设定模拟事件；支持模型生成安排，以及核对自己填写的公交和出租排班。无需账户，页面、求解和运行记录均在本地。

## 一 怎样打开

在仓库根目录双击[启动研究平台.cmd](../../启动研究平台.cmd)。启动后会自动打开浏览器，通常地址为 `http://127.0.0.1:8765`。如果服务已经运行，会打开现有服务；端口被占用时在8765至8775之间选择空闲端口。

本工作区已有可运行的Python、NumPy和SciPy环境，启动脚本会自动寻找。另一台电脑首次使用时，需要安装Python 3.12及[原型依赖](../接续运输优化原型/requirements.txt)：

```powershell
python -m pip install -r 04_建模/接续运输优化原型/requirements.txt
```

关闭网页不会停止正在进行的计算。页面内可取消当前计算；在“使用说明”中可结束本地服务。下次仍双击同一启动文件即可。

## 二 第一次先走通12人示例

1. 点击“12人手算示例”。这些数值全部为教学模拟参数。
2. 在“事件与目标”查看12人、1小时进入、200元预算及开始时间。
3. 在“需求与方向”查看一条进入过程和一个方向；12人每10分钟进入2人。
4. 在“资源与手工安排”查看1辆6座公交、最多2班、无基础服务及出租增援。
5. 到“校验与运行”，校验后点击“开始计算”。输入结构通过不代表必然有可行方案。
6. 在结果页查看08:30、09:00两班离站、累计等待240人分钟、平均等待20分钟、费用200元。
7. 点击“下载完整验证包”，或打开报告打印。将结果排班复制到手工模式再核对，可以得到同一等待和完成结果。

以上示例开始时间默认为2026年10月20日08:00；改变日期不会改变相对分钟下的计算关系。

## 三 用于其他事件的完整流程

| 步骤 | 需要填写什么 | 完成后检查什么 |
|---|---|---|
| 事件与目标 | 名称、真实背景或模拟属性、研究人群、来源、开始时间、进入时长、提前量、预算、候客与完成目标 | 事件受影响人数是否等于本研究接续人数；完成是否指离开指定候客系统 |
| 需求与方向 | 每小时新增人数、一条或多条可能过程、接续方向及份额、初始候客、基础剩余能力、面积、运行与下游能力 | 每条曲线总量一致，方向份额加总100%；初始候客不重复计入新增人数 |
| 资源与手工安排 | 公交车辆与班次、登乘和周转、各类窗口、出租服务包、舒适要求；选择优化或手工核对 | 车辆不等于班次，服务名额不等于出租车辆，所有时刻按相对分钟解释 |
| 校验与运行 | 检查错误及提示，设置每阶段求解限时，实际运行 | 校验通过、求解可行及独立复核通过分别判断；限时不等于无解 |
| 结果与导出 | 查看各过程结果、候客曲线、分时核算、车辆排班、预约及求解状态 | 保留运行时输入；后续修改须形成新运行，比较时统一人群、目标、预算和约束 |

“新建模拟事件”提供可修改初值，需逐项调整为自己的设定，不会保留虹桥事实。可以用生成按钮建立均匀、前段、中段或后段集中过程；也可逐小时填写。生成过程不代表估计出了真实概率。

如果资料不足，明确填写研究假设和设定理由。平台检查数据结构及计算关系，不会自动把报道人次、计划班次或录入者声明认证为实际剩余能力。

修改模板后，请在事件说明中记录改动依据。模板附带的历史事实和来源仍是原始背景，具体模型数值以本次输入为准；如需修改逐项证据声明，可使用“查看完整参数”编辑后重新校验。

## 四 怎样手动验证一个排班

第三步选择“核对我填写的手工排班”，然后填写：

- 公交：每班车辆编号、方向、相对离站分钟。开始登乘及返回时间由输入参数推算。同一车辆冲突、站位冲突或窗口不合会被拒绝。
- 出租：方向、一个时间步的开始分钟、预约服务人数。名额须为每服务包人数的整数倍，同方向同段会合并。

不填写增援排班时，核对的是仅使用基础服务的结果。手工模式按“只看当前队列、基础→出租→公交、同方向先到先服务”执行；它检验这一规则下的表现，不为手工资源另求最优旅客分配。

可点击优化结果中的“将此排班放入手工核对”，调整某一班或某一段预约后重新计算。原结果仍保留，便于比较删减班次、延后资源或改变需求的影响。

**两种失败须区分：**排班本身违反资源条件时，平台先阻止运行；排班合法但超候客上限或未按时完成时，结果标为“目标未全部通过”，并报告截止剩余人数。未完成过程的完整平均等待留空，不能记为0。

## 五 输出什么，怎样手工核算

| 文件 | 用途 |
|---|---|
| 输入情景卡.json | 保留全部条件、来源及声明；可重新导入平台 |
| 完整计算结果.json | 运行设置、求解状态和差距、服务过程、独立核对、输入及代码版本哈希 |
| 公交排班.csv | 逐辆车开始登乘、离站、到节点、再次可投入时刻 |
| 出租预约.csv | 各方向各时间步服务名额及预约费用 |
| 过程指标与对照.csv | 本次安排与仅基础服务的候客、等待、完成、站立及通过情况 |
| 分时核算明细.csv | 每过程逐段新增、服务前候客、服务、服务后候客及守恒残差 |
| 验证报告.html | 含曲线和表格的独立报告，可用浏览器打印或另存为PDF |
| 复现说明.txt | 复现入口与求解差异的解释 |

“完整验证包”将以上八个文件打包，不需要再手动逐个收集。

手工核算可按以下顺序：

1. 核对总量：新增人数加初始候客等于任务总量，每条允许过程分别计算。
2. 核对队列：上段服务后候客加本段新增等于本段服务前候客；再减本段实际服务得到服务后候客。
3. 核对时间：公交登乘不能早于准备完成，同车下一班登乘不能早于上一班返回；到节点时仍应开放。
4. 核对预算：公交班次费用加全部出租预约包费用，闲置预约仍计费。
5. 核对舒适和目标：核定人数、站立密度、站立人分钟、候客上限及完成截止均要检查。

页面结果与导出表采用同一运行记录。平台只保存最近100条运行的列表展示，原记录不会自动删除；输入与验证包可主动导出分享。

## 六 虹桥示例如何使用

“虹桥真实背景示例”承接2023年12月14日降雪晚点的公开事件背景。6000人、方向、基础能力、车辆、费用与舒适阈值均为明确假设，不能作为当年实际需求和排班回放。

在24000元预算上限、四种进入过程、1000人候客上限及05:30截止条件下，平台可生成19班公交、1600个出租服务名额的共同安排。主结果可与[八页模型报告](../../07_成果输出/接续运输优化原型与虹桥事件背景实验-2026-10-19.md)核对。平台的基础对照统一在本次完成截止停止，未完成的平均等待留空；旧实验延长观察至07:00的指标不能直接混用。

## 七 当前适用范围

第一版支持1至12小时进入、最多6个接续方向、8种允许过程及180个时间段。各过程新增总人数相同、方向份额固定；基础能力按方向为常数，增援服务有窗口。本版采用同质备用公交，去程与回程时长相同；出租以服务名额约束，不是逐辆车周转。

时间步可选5、10、15、20或30分钟。旅客段初批量进入，服务段末完成；改变时间步后应重新核对出租每步上限和手工排班。公交登乘向上取整；非整步运行时间按既有模型归并下游到达时段。分钟复算也采用同一时间约定。

公交舒适采用座位、站立密度和站立持续时间；等待及候客密度分别显示，没有未经标定的主观满意度总分。感知舒适函数、不同人群接受方式、逐人登乘和执行中滚动调整尚未实现。

## 八 文件与运行维护

- `core.py`：平台参数核对、手工排班适配、结果与导出。现有模型和独立核算程序保持原版本。
- `server.py`：仅监听127.0.0.1；保存、异步运行、进度、取消和文件下载。
- `worker.py`：每次运行独立进程，保存阶段进度、结果、环境版本及异常日志。
- `web/`：中文表单、结果页面与可视曲线；无外部脚本、字体或图表依赖。

用户输入与运行记录位于 `06_实验验证/平台运行记录/`，已排除Git同步。服务日志位于 `.qa/platform_service/`。输入卡和完整验证包由使用者主动导出；平台没有账号、云端存储和远程多人协作。

技术启动与检查：

```powershell
python 04_建模/交互验证平台/server.py --port 8765
python 06_实验验证/优化模型验证/test_platform.py
```
